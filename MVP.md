
# BudgetPlanner — MVP

## 1. Цель проекта

BudgetPlanner — консольное приложение для планирования личного бюджета и прогнозирования движения денежных средств.

Главная задача MVP — помочь пользователю с ограниченным бюджетом понять:

- Достаточно ли средств для выполнения финансового плана.
- Когда может возникнуть нехватка денег.
- Какой суммы не хватит.
- Какие расходы приводят к возникновению дефицита.
- Сколько денег останется к окончанию периода планирования.

Приложение должно не просто учитывать доходы и расходы, а оценивать выполнимость финансового плана.

## 2. Основной пользовательский сценарий

Пользователь:

1. Указывает текущие остатки на своих финансовых счетах.
2. Добавляет планируемые поступления.
3. Добавляет регулярные и разовые расходы.
4. Отмечает расходы как обязательные или необязательные.
5. При необходимости указывает счёт, с которого должен оплачиваться конкретный расход.
6. Выбирает период планирования: дату начала и дату окончания.
7. Запускает финансовый расчёт.
8. Получает прогноз движения денежных средств и список критичных событий.

Пользователь может добавлять, изменять и удалять исходные данные до запуска расчёта.

## 3. Функциональные требования MVP

### 3.1. Финансовые счета

- Хранение нескольких независимых счетов.
- Хранение названия и текущего остатка каждого счёта.
- Возможность использовать наличные средства как отдельный счёт.
- Выбор счёта по умолчанию для расчёта.
- Поддержка изменения исходных остатков.

### 3.2. Доходы

- Разовые и регулярные доходы.
- Сумма дохода.
- Дата начала поступлений.
- Периодичность.
- Необязательная дата окончания регулярных поступлений.
- Обязательное указание счёта зачисления.

### 3.3. Расходы

- Разовые и регулярные расходы.
- Сумма расхода.
- Дата начала.
- Периодичность.
- Необязательная дата окончания регулярных расходов.
- Признак обязательного или необязательного расхода.
- Название расхода.
- Необязательный счёт оплаты.

Если счёт оплаты не указан, используется счёт по умолчанию из финансового сценария.

### 3.4. Периодичность

Поддерживаемые варианты периодичности определяются перечислением FinancialFrequency.

Для ежемесячных операций применяется правило календарного месяца: если исходное число отсутствует в месяце, используется последний день этого месяца.

При этом исходная дата сохраняется. Например:

- 31 января;
- 28 февраля;
- 31 марта;
- 30 апреля.

Это позволяет избежать постепенного смещения даты регулярной операции.

### 3.5. Финансовый сценарий

Сценарий объединяет исходные данные для одного расчёта:

- финансовые счета и начальные остатки;
- доходы;
- расходы;
- разовые финансовые операции;
- дату начала планирования;
- дату окончания планирования;
- счёт по умолчанию.

Исходные данные сценария должны быть отделены от результата расчёта.

### 3.6. Распределение расходов по счетам

Для оплаты расхода применяется следующий алгоритм:

1. Если у расхода указан конкретный счёт, сначала используется он.
2. Если счёт не указан, сначала используется счёт по умолчанию.
3. Если на выбранном счёте недостаточно денег, с него списывается доступная сумма.
4. Оставшаяся сумма распределяется между другими счетами, начиная со счёта с наибольшим текущим остатком.
5. При равных остатках используется стабильный порядок — порядок счетов в списке пользователя.
6. Один расход может быть оплачен с нескольких счетов.
7. Если средств на всех счетах недостаточно, фиксируется частичная оплата и размер дефицита.

Исходная сумма расхода не изменяется при частичной оплате.

Фактические списания должны сохранять информацию об использованном счёте и сумме.

### 3.7. Финансовый расчёт

- Формирование последовательности финансовых событий на выбранный период.
- Учет поступлений и списаний.
- Расчет остатков по каждому счёту.
- Расчет общего остатка собственных средств.
- Учет частично оплаченных расходов.
- Определение первой даты возникновения дефицита.
- Определение размера нехватки средств.
- Определение расходов, после которых возник дефицит.

Переводы между собственными счетами не должны изменять общий объём собственных средств.

### 3.8. Результат расчёта

Пользователь получает:

- Прогноз остатков на каждый день или после каждого финансового события.
- Первую дату возникновения дефицита.
- Размер недостающей суммы.
- Список расходов, после которых возник дефицит.
- Разделение обязательных и необязательных расходов.
- Итоговый остаток на конец периода.

Дополнительно предусматривается повторный расчёт без необязательных расходов. Это позволяет оценить, как отказ от желаемых трат повлияет на финансовый прогноз.

## 4. Архитектура MVP

Предполагаемые основные компоненты:

### Модели исходных данных

- FinancialAccount
- Income
- Expense
- Transaction
- BudgetScenario

### Расчётные компоненты

- Генератор финансовых событий — преобразует регулярные операции в конкретные события с датами и суммами.
- BudgetCalculator — выполняет расчёт движения денежных средств и распределение расходов по счетам.
- BudgetReport — хранит результат расчёта и информацию о критичных событиях.

Названия и ответственность компонентов могут уточняться по мере реализации.

## 5. Хранение данных

- Использование JSON для сохранения и загрузки данных.
- Сохранение исходных финансовых сценариев.
- Сохранение результатов расчёта.
- Возможность повторной загрузки сохранённого сценария.

## 6. Тестирование

Обязательно проверить:

- Корректность расчёта регулярных доходов и расходов.
- Корректность ежемесячных дат, включая переходы между месяцами.
- Корректность расчёта остатков по нескольким счетам.
- Распределение расходов между счетами.
- Частичную оплату при нехватке средств.
- Определение первой даты дефицита.
- Разделение обязательных и необязательных расходов.
- Повторный расчёт без необязательных расходов.
- Сохранение и загрузку сценария.

## 7. Что не входит в MVP

Следующие функции откладываются до завершения первой рабочей версии:

- Кредитные карты и кредитные лимиты.
- Льготные периоды и графики погашения задолженности.
- Расширенная модель заёмных средств.
- Автоматическая оптимизация расходов.
- Автоматический перенос платежей на другие даты.
- Автоматическое изменение бюджета.
- Сложные рекомендации пользователю.
- Сравнение большого количества сценариев.
- Графический интерфейс.
- Графики и визуальная аналитика.
- Резервное копирование и восстановление данных.

## 8. Критерии готовности MVP

MVP считается готовым, когда пользователь может:

1. Создать финансовый сценарий с несколькими счетами.
2. Указать начальные остатки, доходы и расходы.
3. Выбрать произвольный период планирования.
4. Запустить расчёт финансового прогноза.
5. Увидеть, достаточно ли денег для выполнения плана.
6. Узнать дату и размер первого дефицита.
7. Увидеть, какие расходы привели к дефициту.
8. Получить прогноз остатка на конец периода.
9. Повторить расчёт без необязательных расходов.
10. Сохранить сценарий и загрузить его позднее.

**Главный критерий:** приложение должно корректно определить, выполним ли заданный финансовый план при имеющихся собственных средствах и планируемых поступлениях.
