# 2. Назначение приложения

BudgetPlanner — приложение для финансового моделирования и планирования личного бюджета.

Это НЕ приложение для постоянного отслеживания банковских операций пользователя.

Основной принцип работы:

1. Пользователь запускает приложение.
2. Вводит исходные финансовые данные.
3. Указывает остатки на банковских счетах и сумму наличных.
4. Добавляет ожидаемые доходы.
5. Указывает обязательные и необязательные расходы.
6. Вводит информацию о кредитных картах и задолженности.
7. Задаёт финансовый резерв и бюджет повседневных расходов.
8. Запускает расчёт.
9. Получает прогноз финансового положения на следующие 6 месяцев.
10. Получает несколько вариантов использования денежных средств, рекомендации и анализ рисков.
11. Сохраняет расчёт для последующего просмотра и сравнения.

Каждый расчёт является независимым финансовым сценарием.

**Критически важное требование:**

Новый расчёт не должен учитывать исходные данные предыдущего расчёта.

Пользователь должен иметь возможность:
- создавать новые сценарии;
- сохранять их;
- открывать ранее сохранённые сценарии;
- просматривать исходные данные и результаты;
- сравнивать разные сценарии;
- удалять ненужные сценарии.

Сохранённые сценарии не должны автоматически влиять друг на друга.

# 3. Основные финансовые требования

## 3.1. Горизонт планирования

Прогноз должен охватывать следующие 6 месяцев.

## 3.2. Валюта

На текущем этапе используется только RUB.

Не нужно зашивать знак ₽ и валютные предположения в бизнес-логику отдельных классов.

Предусмотреть архитектуру, позволяющую в будущем добавить:
- отдельную модель валюты;
- несколько валют;
- сервис конвертации валют;
- единые правила отображения денежных сумм.

Сейчас достаточно единой настройки базовой валюты приложения.

Не создавать полноценную валютную систему преждевременно.

## 3.3. Финансовые счета

Пользователь может иметь неограниченное количество финансовых счетов.

Необходимо поддерживать:
- банковские счета;
- наличные средства.

Наличные также представляются отдельными финансовыми счетами типа Cash.

Каждый счёт имеет собственный баланс.

Закрытие банковских счетов и постоянное отслеживание их состояния не требуются.

Пользователь вводит исходные остатки перед каждым новым расчётом.

## 3.4. Доходы

Необходимо поддерживать:
- разовые доходы;
- регулярные доходы;
- различные периоды поступления;
- дату начала;
- необязательную дату окончания;
- изменения суммы дохода с определённой даты;
- историю изменений суммы.

Все введённые пользователем поступления считаются гарантированными в рамках конкретного сценария.

Пользователь самостоятельно создаёт разные сценарии с различными предположениями о доходах.

## 3.5. Расходы

Необходимо поддерживать:
- разовые расходы;
- регулярные расходы;
- обязательные расходы;
- необязательные расходы;
- дату платежа;
- периодичность;
- изменение суммы с определённой даты.

Для каждого расхода обязательно указывается счёт, с которого он будет оплачен.

## 3.6. Финансовые операции

Необходимо реализовать:
- поступления;
- списания;
- переводы между собственными счетами.

Переводы между собственными счетами не являются доходом или расходом.

Должен быть механизм контроля корректности операций.

## 3.7. Кредитные карты

Требуется полноценная модель кредитных карт.

Необходимо учитывать:
- кредитный лимит;
- текущую задолженность;
- доступный кредитный лимит;
- льготный период;
- дату формирования выписки;
- дату обязательного платежа;
- сумму полного погашения;
- будущие обязательства по погашению.

Предполагается, что пользователь своевременно и полностью погашает задолженность в рамках льготного периода. Проценты в основной модели не рассчитываются.

Нужно предусмотреть:
- разрешение или запрет использования кредитных средств для снятия наличных и переводов;
- индивидуальный лимит снятия наличных для каждой карты.

Погашение кредитной карты должно учитываться в будущих обязательствах.

Не смешивать собственные средства и доступный кредит.

## 3.8. Бюджет повседневных расходов

Пользователь может:
- отключить повседневный бюджет;
- установить ежедневный бюджет;
- установить месячный бюджет.

Программа может автоматически уменьшать установленный бюджет при обнаружении дефицита.

Программа не может самостоятельно увеличивать бюджет без согласия пользователя.

## 3.9. Финансовый резерв

Пользователь задаёт размер финансового резерва.

Свободные средства рассчитываются по принципу:

Свободные средства = Прогнозируемые собственные средства − Обязательные будущие расходы − Финансовый резерв.

При этом необходимо корректно учитывать временное распределение денежных средств и не допускать двойного вычитания обязательств.

# 4. Основные архитектурные принципы

При разработке придерживайся следующих принципов.

### 4.1. Независимость бизнес-логики от интерфейса

Финансовые модели и расчётная логика не должны зависеть от консольного или графического интерфейса.

В будущем графический интерфейс должен использовать существующую финансовую логику, а не содержать собственные реализации финансовых расчётов.

### 4.2. Разделение ответственности

Не объединяй в одном классе:
- исходные финансовые данные;
- операции;
- финансовые расчёты;
- результаты прогнозирования;
- отображение информации.

Каждая сущность должна иметь понятную ответственность.

### 4.3. Независимость сценариев

Каждый финансовый сценарий должен иметь собственные исходные данные и результаты.

Нельзя использовать глобальное изменяемое состояние, которое приводит к переносу данных между сценариями.

### 4.4. Надёжность денежных расчётов

Для денежных сумм использовать decimal, а не double или float.

Не допускать:
- отрицательных остатков там, где они недопустимы;
- двойного учёта переводов;
- двойного учёта кредитных обязательств;
- смешивания собственных и заёмных средств;
- некорректного расчёта доступных средств.

Проверять граничные случаи.

### 4.5. Развитие без преждевременного усложнения

Не добавляй абстракции, интерфейсы, сервисы и дополнительные классы без понятной необходимости.

Не нужно создавать сложную архитектуру ради соответствия модным шаблонам.

Но и не следует упрощать финансовую модель таким образом, чтобы впоследствии пришлось полностью её переделывать.

# 7. Правила совместной разработки

Это один из самых важных разделов.

Я изучаю C# и хочу понимать, что именно мы разрабатываем.

Поэтому всегда придерживайся следующей последовательности:

### Шаг 1. Разбираем назначение класса

Объясни:
- зачем нужен класс;
- какую ответственность он несёт;
- с какими другими моделями взаимодействует;
- почему его необходимо выделить в отдельную сущность.

### Шаг 2. Обсуждаем необходимые свойства

Для каждого свойства объясни:
- его назначение;
- почему выбран именно этот тип данных;
- обязательно ли оно;
- какое значение должно использоваться по умолчанию;
- не дублирует ли оно информацию из других моделей.

Не добавляй свойства просто на всякий случай.

### Шаг 3. Пишем код вместе

Не выдавай сразу большое количество готового кода.

Предпочтительно:
- небольшие фрагменты;
- последовательное добавление свойств;
- объяснение синтаксиса C#;
- разбор конструкций языка;
- объяснение архитектурных решений.

Я должен понимать код, а не просто копировать его.

### Шаг 4. Проверяем работоспособность

После реализации:
- проверяем компиляцию;
- запускаем приложение;
- проверяем ожидаемые результаты;
- рассматриваем граничные случаи;
- исправляем обнаруженные ошибки.

Не утверждай, что запускал сборку или тесты, если фактически этого не делал.

### Шаг 5. Делаем Git-коммит

После завершения логического этапа:
- проверяем изменения;
- формируем понятное сообщение коммита;
- при необходимости предлагаем команду Git;
- проверяем, что коммит относится к завершённому этапу.

Не переходи к следующему крупному этапу без завершения текущего.
