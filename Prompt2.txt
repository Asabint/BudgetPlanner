# 1. Назначение приложения

BudgetPlanner — приложение для финансового моделирования личного бюджета.

Это не приложение для постоянного отслеживания банковских операций. Пользователь вводит исходные финансовые данные, запускает расчёт и получает прогноз своего финансового положения на следующие 6 месяцев.

Основные задачи приложения:

- учёт собственных денежных средств;
- учёт банковских счетов и наличных;
- учёт кредитных карт;
- учёт регулярных и разовых доходов;
- учёт обязательных и желаемых расходов;
- прогнозирование денежных потоков;
- выявление временного дефицита средств;
- анализ финансового положения на выбранном горизонте.

В первой версии приложение должно объективно показывать последствия финансовых планов пользователя. Автоматические рекомендации пока не нужны.

В дальнейшем планируется добавить:
- оптимизацию желаемых расходов;
- подбор возможной даты совершения покупки;
- сравнение финансовых сценариев;
- сохранение и загрузку сценариев;
- сравнение результатов нескольких сценариев.

# 5. Архитектурные требования

## Финансовые сценарии

Пользователь должен иметь возможность:
- создавать независимые сценарии;
- вводить исходные данные для каждого сценария;
- запускать расчёт;
- сохранять исходные данные и результаты;
- открывать сохранённые сценарии;
- сравнивать сценарии;
- удалять сценарии.

Каждый новый расчёт должен быть независим от предыдущего.

В будущем предполагается сущность `FinancialScenario`, содержащая:
- исходные финансовые данные;
- результаты расчётов;
- аналитику;
- метаданные сценария;
- версию алгоритма расчёта.

Пока создавать её преждевременно.

## Горизонт расчёта

Основной горизонт прогноза — 6 месяцев.

Важно анализировать движение средств по датам, а не только суммарные остатки на конец периода.

Даже если итоговый баланс положительный, внутри периода может возникнуть временный дефицит.

## Валюта

Пока используется только RUB.

Не зашивай символ валюты и валютные предположения в бизнес-логику отдельных моделей.

В дальнейшем можно добавить отдельную настройку базовой валюты и сервис конвертации.

# 6. Согласованные финансовые правила

## Финансовые счета

- Пользователь может иметь неограниченное количество счетов.
- Наличные представлены отдельным типом финансового счёта.
- Пользователь вводит исходный остаток при каждом расчёте.
- Отрицательные остатки запрещены.
- Закрытие счетов не требуется.
- Название счёта пользователь задаёт самостоятельно.
- Название банка хранить не нужно.
- `FinancialAccount.Balance` содержит исходный остаток, а не прогнозируемый.

## Карты

Предусмотрены дебетовые и кредитные карты.

К одному финансовому счёту может быть привязана только одна карта — дебетовая либо кредитная.

Кредитная карта:
- имеет кредитный лимит;
- имеет текущий долг;
- доступный кредит рассчитывается как `CreditLimit - Debt`;
- `CreditLimit >= 0`;
- `Debt >= 0`;
- `Debt <= CreditLimit`.

Предполагается своевременное полное погашение долга в льготный период. Проценты пока не моделируются.

В перспективе будут добавлены:
- дата выписки;
- дата платежа;
- продолжительность льготного периода;
- правила снятия и перевода кредитных средств.

## Доходы

Доходы могут быть:
- разовыми;
- еженедельными;
- раз в две недели;
- ежемесячными.

Все введённые пользователем доходы считаются гарантированными в рамках сценария.

У доходов предусмотрена история изменения суммы.

`IsExpected` удалён и возвращать его не нужно.

Отдельный `Id` для доходов пока не требуется.

## Расходы

Расходы разделяются на обязательные и желаемые.

Обязательные расходы должны учитываться в прогнозе как необходимые.

Желаемые расходы учитываются в прогнозе, но могут быть предметом дальнейшего анализа.

Приоритет расходов пока не используется.

Для первой версии желаемая покупка задаётся конкретной датой.

Для регулярных расходов:
- `StartDate` — дата первого платежа;
- `EndDate` — дата последнего платежа включительно;
- `EndDate == null` — расход не имеет установленной даты окончания и учитывается в пределах горизонта прогноза.

Периодичность `Yearly` не используется.

# 9. Текущий этап разработки — Expense

Сейчас мы работаем над моделью `Expense`.

Согласованный набор свойств:

| Свойство | Тип | Назначение |
|---|---|---|
| `Name` | `string` | Необязательное описательное название |
| `Amount` | `decimal` | Сумма расхода |
| `Frequency` | `FinancialFrequency` | Периодичность |
| `StartDate` | `DateTime` | Дата первого или единственного платежа |
| `EndDate` | `DateTime?` | Дата последнего платежа |
| `IsMandatory` | `bool` | Обязательный или желаемый расход |

Согласованные правила:

1. `Amount` строго больше нуля.
2. `Name` необязателен, не участвует в расчётах.
3. `StartDate` обязателен.
4. `EndDate` может быть `null`.
5. Если `EndDate` задан, он не может быть раньше `StartDate`.
6. Если `Frequency == Once`, `EndDate` должен быть `null`.
7. Для регулярных расходов `EndDate` может быть задан или отсутствовать.
8. Для дат учитывается только календарная дата, без времени.
9. Неизвестные значения `FinancialFrequency` должны отклоняться.
10. `IsMandatory` по умолчанию `false`.

Информационные сообщения пользователю должны формироваться интерфейсом, а не самой финансовой моделью.

Исключения используются для нарушения правил модели.

Автоматическое обнуление `EndDate` при установке `Frequency = Once` допустимо.

## Текущая реализация Expense

Последний вариант кода:

```csharp
using BudgetPlanner.Models.Enums;

namespace BudgetPlanner.Models;

public class Expense
{
    private decimal _amount;

    public string Name { get; set; } = string.Empty;

    public decimal Amount
    {
        get => _amount;
        set
        {
            ArgumentOutOfRangeException.ThrowIfNegativeOrZero(value);
            _amount = value;
        }
    }

    public FinancialFrequency Frequency
    {
        get;
        set
        {
            if (!Enum.IsDefined(typeof(FinancialFrequency), value))
            {
                throw new ArgumentOutOfRangeException(nameof(value));
            }

            field = value;

            if (value == FinancialFrequency.Once)
            {
                EndDate = null;
            }
        }
    }

    public DateTime StartDate
    {
        get;
        set
        {
            if (EndDate.HasValue && value.Date > EndDate.Value.Date)
            {
                throw new ArgumentOutOfRangeException(nameof(StartDate));
            }

            field = value.Date;
        }
    }

    public DateTime? EndDate
    {
        get;
        set
        {
            if (Frequency == FinancialFrequency.Once)
            {
                field = null;
                return;
            }

            if (value.HasValue && value.Value.Date < StartDate.Date)
            {
                throw new ArgumentOutOfRangeException(nameof(EndDate));
            }

            field = value?.Date;
        }
    }

    public bool IsMandatory { get; set; }
}
```

Это последний вариант реализации, но он ещё не завершён.
